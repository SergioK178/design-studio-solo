# ИМЭКС — B2B-каталог медицинских изделий и расходных материалов

**Тип:** редизайн и переразработка B2B-витрины действующей компании (оптовая/розничная торговля медизделиями и расходными материалами, Санкт-Петербург) — каталог, заявка на КП, контентные страницы.
**Роль:** дизайн, фронтенд, модель данных, миграция каталога, инфраструктура — под ключ.
**Статус:** активная разработка, демо-сборка — Vercel Preview (static-режим без CMS); production VPS-деплой подготовлен, но ещё не запущен на боевой домен.

---

## Задача

У заказчика уже был работающий сайт (оптовая торговля лекарствами и медизделиями), но старая версия не выдерживала ни объём каталога, ни требования к доверию B2B-покупателя. Нужен был не косметический рефреш, а новая основа:

- превратить кустарный каталог (старый сайт + PDF-прайсы производителей) в структурированные данные без потери исходных артикулов;
- сделать интерфейс закупщика — не интернет-магазин, а быстрый путь «нашёл → сравнил варианты → собрал заявку → получил КП»;
- дать контент-менеджеру редактируемую CMS без участия разработчика на каждый чих;
- не тянуть за собой личный кабинет, остатки, 1С и другие вещи, которые не нужны на первом этапе, но заложить архитектуру так, чтобы их можно было добавить позже без переписывания;
- держать честный дизайн: без фейковых data-чипов и дублирующих CTA в hero, без ощущения generic AI-лендинга.

---

## Результат кратко

- Единая модель «группа товара → варианты» на устойчивом `variant_uid`, сквозная от миграции до карточки товара.
- Двухступенчатый конвейер миграции каталога: нормализация старого сайта и PDF-прайсов → аудит → AI-курирование под жёсткими guardrails → валидация → импорт в Directus.
- Каталог рендерится из живого Directus; локальный JSON — это только dev-fallback, если CMS недоступна, а не источник правды.
- Заявка на КП (Quote Drawer) вместо корзины интернет-магазина: подбор вариантов, drawer, отправка в Directus как `leads`.
- Editorial-дизайн (Spectral + Manrope + IBM Plex Mono, glassmorphism-панели) вместо шаблонного «нейролендинга»; hero — без фейковых метрик и задвоенных CTA.
- Двойной build-режим: боевой server-mode на Node/VPS и static Vercel-preview для показа структуры без поднятой CMS.

---

## Стек

**Frontend**
- **Astro 5** (server output) + **TypeScript** (строгий режим)
- **Tailwind CSS v4** через `@tailwindcss/vite`, дизайн-токены в `@theme` (oklch-палитра, шрифтовая тройка, тени, радиусы, z-слои)
- **astro-icon** (Phosphor icon set) вместо тяжёлого UI-кита
- Собственные компоненты (`VariantPicker`, `QuoteDrawer`, `ProductCard`, `CatalogState`) — интерактив точечно, без SPA

**Backend / CMS**
- **Directus** — админка и API поверх Postgres, коллекции `categories/products/manufacturers/documents/articles/leads`
- **PostgreSQL** — основная база каталога и заявок
- **MinIO (S3-compatible)** — хранение изображений и документов отдельно от приложения
- **Astro server endpoint** (`POST /api/leads`) — тонкий слой между формой и Directus, чтобы не открывать публичную запись напрямую в CMS

**Данные и миграция**
- Node-скрипты (`scripts/*.mjs`) — нормализация, аудит, сборка и валидация каталога v2
- **Zod** — валидация лидов на сервере
- `node --test` — unit-тесты хелперов каталога (`variant_uid`, `display_title` и т.д.)

**Инфраструктура / деплой**
- **VPS (Ubuntu)** без PaaS: Astro как `systemd`-сервис, Directus/Postgres/MinIO в Docker Compose
- **Caddy** — reverse proxy и TLS, публично только сайт и CMS-домен
- Доставка релиза — артефакт по `rsync`/SSH, symlink-переключение `current`, healthcheck, откат
- **Vercel** — только временный static preview (без БД) для показа структуры

## Ключевые решения и практики

### 1. B2B-заявка вместо интернет-магазина
Осознанный отказ от полноценной корзины: у медизделий нет публичных цен и остатков в реальном времени, поэтому основной сценарий — «собрать позиции → отправить заявку на КП», а не «оплатить онлайн». `QuoteDrawer` копит выбранные варианты (localStorage), `VariantPicker` даёт выбрать типоразмер/упаковку конкретного товара до попадания в заявку, а `POST /api/leads` валидирует состав заявки через Zod (включая до 50 позиций с `variantUid`, `packageQty`, `manufacturerName`) и создаёт лид в Directus. Личный кабинет, роли покупателей, персональные цены и остатки — сознательно отложены до подтверждения необходимости, а не потому что «не успели».

### 2. Модель «группа + вариант» на устойчивом `variant_uid`
Товар — это группа (`product_groups`) с несколькими вариантами (`product_variants`): размер, длина, упаковка. Ключ связки — не порядковый номер и не отображаемый артикул, а стабильный `variant_uid`, который переживает повторные импорты и не расходится с исходными артикулами поставщика (`article_raw` хранится нетронутым отдельно от `display_sku`). Это решение сложилось не сразу — история коммитов показывает явную итерацию (`keep source articles verbatim, key site variants by variant_uid` → `stop suffixing source articles` → `validate variant_uid, require public display fields`), то есть модель была осознанно исправлена после того, как более простой подход (суффиксы к артикулам) начал терять данные при повторной синхронизации.

### 3. Конвейер миграции каталога с AI-курированием под guardrails
Исходные данные — это старый сайт и PDF-прайсы производителей, разнородные и грязные. Конвейер (`catalog:v2:normalize → clean → audit → prepare-ai → apply-ai → build → validate → import`) приводит их к единой схеме:
- **Аудит** размечает каждую группу/вариант флагами (`missing_title`, `no_variants`, `public_but_not_verified`, `source_pdf` и т.д.) и считает severity (`clean/warning/problem`), включая поиск задублированных артикулов внутри группы.
- **AI-курирование** оформлено как батчи JSON с явным протоколом: LLM может только предлагать `suggested_title/description/category`, `qa_status`, `confidence_score` — но не имеет права трогать артикулы, `variant_uid`, `group_slug` или удалять/сливать позиции.
- **Приёмка предложений** (`apply-ai-curation-suggestions.mjs`) — это не доверчивое слияние, а валидатор: отклоняет предложения с неизвестными/защищёнными полями, несуществующей категорией, несоответствием подкатегории родителю, некорректным `confidence_score`; все отклонения уходят в CSV-отчёт с причиной, ничего не пропадает молча.
- Результат — детерминированная сборка `catalog-v2.json` с фингерпринтом источника, которую можно провалидировать и импортировать в Directus повторно без риска расхождения.

### 4. Источник данных — живой Directus, а не сид
Витрина (`getCatalog()`) сначала пытается получить каталог из Directus (`categories/manufacturers/products` через REST + auth-токен), и только если Directus недоступна или не настроена — откатывается на локальный `src/data/catalog.json`, чтобы интерфейс оставался рабочим для разработки офлайн. Это dev-fallback, а не альтернативный источник правды: контент-менеджер правит товары в Directus, а не в JSON в репозитории.

### 5. Дизайн против «нейролендинга»
Осознанная работа против визуальных штампов сгенерированных B2B-сайтов:
- editorial-контраст в типографике — **Spectral** (антиква) на заголовках и крупных числах, **Manrope** в теле и интерфейсе, **IBM Plex Mono** — технический слой (артикулы, микролейблы, индексы секций), вместо одного безликого Inter/Manrope на всё;
- glassmorphism-слой — полупрозрачные `glass-panel`/`glass-card` на oklch-палитре, а не плоские карточки;
- hero и карточки без «мусора»: никаких фейковых дата-чипов ради ощущения насыщенности и без задвоенных CTA рядом — решение сознательно скорректировано по ходу работы (коммит `overlap hero — clean, no data chips per user feedback`) после того, как более «наполненный» вариант читался как шаблонный AI-лендинг;
- собственный blueprint/line-art SVG-слой и scroll-reveal вместо стоковых иконок и градиентных заглушек.
Дизайн-направление и типографическая шкала зафиксированы в отдельном спеке (`docs/imex_tech_design_implementation_spec.md`) с точными слотами под кастомные иллюстрации — так дизайнер и разработка не расходятся в деталях.

### 6. Заявки: защита и обратная связь
`POST /api/leads` — Zod-схема на сервере (телефон, email, до 50 позиций заявки), honeypot-поле (`website`, обязано быть пустым), простое in-memory rate-limiting (5 заявок / 10 минут на IP с учётом `x-forwarded-for`), явные коды ответов (`429` лимит, `503` не настроен Directus, `502` ошибка сохранения) — вместо тихого "не отправилось".

### 7. Два build-режима без раздвоения кода
Один и тот же Astro-проект собирается в двух режимах через `astro.config.mjs`: боевой `output: server` + `@astrojs/node` (standalone) для VPS, и `@astrojs/vercel` при `VERCEL_STATIC_PREVIEW=true` — для быстрого показа структуры сайта на Vercel без поднятой CMS (каталог из seed-JSON, заявка работает как mock-успех без реальной отправки). Переключение — одной env-переменной, а не отдельной веткой репозитория.

### 8. Инфраструктура и деплой без PaaS
- **VPS**: Astro — `systemd`-сервис, Directus/Postgres/MinIO — Docker Compose, **Caddy** — reverse proxy и TLS; наружу открыты только `22/80/443`, Postgres и MinIO без публичных портов.
- Релиз — `rsync`/SSH-доставка артефакта, атомарное переключение симлинка, healthcheck, хранение последних релизов с ротацией.
- Секреты рантайма живут вне релизов (`shared/.env`, права `600`), отдельно от билд-тайм переменных.
- Отдельные bootstrap-скрипты (`remote-bootstrap-directus.sh`, `bootstrap-directus-v2.mjs`) поднимают коллекции и связи Directus (в т.ч. читаемые m2o-шаблоны и list-layouts по умолчанию) воспроизводимо, без ручной настройки через UI.

### 9. Инженерная гигиена
- Строгий TypeScript, Zod на границе сети, unit-тесты (`node --test`) для хелперов миграции (`variant_uid`, синхронизация `display_title` при переименовании группы).
- Каждый шаг конвейера каталога — отдельная CLI-команда (`pnpm catalog:v2:*`) с dry-run-валидацией перед `--apply`, а не один непрозрачный скрипт «сделай всё».
- Единый источник правды по товару — данные не дублируются между Directus-схемой, адаптером каталога и текстами; `docs/content_manager_guide.md` и `docs/catalog_import_fields.md` описывают процесс для контент-менеджера без участия разработчика.

## Что этот проект показывает заказчику

- **Работа с грязными реальными данными**: не «собрали демо на idealized JSON», а провели действующий каталог живой компании (старый сайт + PDF-прайсы производителей) через воспроизводимый конвейер нормализации и аудита без потери исходных артикулов.
- **Осторожное использование AI в продакшн-пайплайне**: LLM ускоряет курирование каталога, но заперта в whitelist полей и проходит через валидатор с логированием отказов — не «просто скормили GPT данные и поверили».
- **Продуктовое мышление под B2B, а не косметика**: заявка на КП вместо витринной корзины, потому что это соответствует тому, как реально закупают медизделия.
- **Инженерная зрелость**: устойчивая модель данных, пережившая собственную переработку по ходу разработки, два build-режима без раздвоения кода, zero-config-по-UI Directus-bootstrap, VPS-деплой без PaaS.
- **Дизайн-дисциплина**: готовность вырезать «мусор» из hero по фидбэку вместо того, чтобы оставить визуально «насыщенный», но нечестный интерфейс.
